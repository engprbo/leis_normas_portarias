verticalJustification

verticalJustification ::= '(' 'verticalJustification'
	( bottomJustify | baselineJustify | middleJustify | caplineJustify | topJustify 
	)
	')'

Used by:

displayAttributes

Description:

VerticalJustification determines the vertical position of the text's bounding box relative to the origin of the text specified in display. For example, if the text origin is at (300, 100) and caplineJustify is specified, the capline of the bounding box (see the following diagram) is placed at the y coordinate of 100.

The default value is baselineJustify.

The values and their meaning are given in the following table.

VerticalJustification
Position of origin
bottomJustify
The bottom of the bounding box.
baselineJustify
The baseline (bottom of capital letters) of the
last line of text.
middleJustify
Halfway between the top and bottom of the
bounding box.
caplineJustify
The capline (top of capital letters) of the first
line of text.
topJustify
The top of the bounding box.

The position of the origin is marked in the following fragments of text.

Example:

(figureGroup small_text
   (displayAttributes 
      (color 0 0 50) 
      (fontRef courier)
      (horizontalJustification (leftJustify))
      (verticalJustification (middleJustify))
      (textHeight 160)) ...)

See also:

fontCapitalHeight fontDescent fontHeight horizontalJustification textHeight

viewGroup

viewGroup ::= '(' 'viewGroup'
	viewGroupNameDef
	viewGroupHeader
	{ comment | userData | viewGroupRef | viewRef } 
	')'

Used by:

cell

Description:

ViewGroup is used to group together views in the same or different clusters of the same cell. ViewRef in this context should therefore not contain a nested cellRef for any purpose. The reason for the grouping may be given in reason.

Example:

(viewGroup VG1
   (viewGroupHeader
      (reason
         "Alternate views with/without power 
         and ground ports"))
   (viewRef SCHEMATIC (clusterRef BASIC))
   (viewRef SCHEMATIC 
      (clusterRef WITH_POWER_AND_GROUND)))

ViewGroup is used in this example to group two views for a reason, indicating that one has power and ground ports but the other does not.

See also:

cluster

viewNameDef

viewNameDef ::= nameDef

Used by:

behaviorView connectivityView logicModelView maskLayoutView pcbLayoutView schematicSymbol schematicView symbolicLayoutView

Description:

A viewNameDef is used to name each view or symbol of a cluster. This name will be referenced in the context of a schematicInstanceImplementation statement.

The scope for view names is provided by the enclosing cluster definition. Different views and symbols within the same cluster must have different names, even if they are different types of view.

There are no semantics associated with the choice of view names within EDIF. It should not be assumed that the choice of names for views has any effect on their interpretation.

Example:

    (cell C  ...
      (cluster CL1 (interface ...)
         (clusterHeader ...)
         (connectivityView V  ...)))

In this example, V is the name of the view being defined.

See also:

cell nameInformation viewNameRef viewRef

viewRef

viewRef ::= '(' 'viewRef'
	viewNameRef
	[ clusterRef ]
	')'

Used by:

clusterConfiguration derivedFrom previousVersion viewGroup

Description:

The viewRef construct is used at any place where there is a need to reference a view. If the view being referenced belongs to a cell which is defined in a different library, then viewRef is required to have a nested clusterRef and cellRef form with a libraryRef form specified within it.

Example:

(viewGroup A (viewGroupHeader ...)    
   (viewRef V1 (clusterRef C1)) 
   (viewRef V2 (clusterRef C1)))

In this example, the viewRef is used to identify the views that make up this viewGroup.

See also:

visible

visible ::= '(' 'visible'
	booleanValue
	')'

Used by:

displayAttributes

Description:

Visible is an attribute of figureGroups (within displayAttributes) which is used to enable or inhibit graphical display. It may be specified within figureGroup to provide a default value throughout a library, or modified within figureGroupOverride. If not specified in either location, a visibility of true is assumed.

Example:

    (display
        (figureGroupOverride redText
            (displayAttributes (visible (false))))
        (transform (origin (pt 125 300))))

This example illustrates a display specification at point (125, 300), which should typically be invisible.

See also:

voltageMap

voltageMap ::= '(' 'voltageMap'
	voltageValue
	')'

Used by:

logicValue

Description:

VoltageMap is an attribute of a logic value used to specify its electrical characteristics. VoltageMap gives a value or range of values to specify the accepted voltage values for the defined logic value. This is scaled according to the units defined by setVoltage.

Example:

(setVoltage (unitRef mV))
...
(logicDefinitions ...
   (logicValue T
      (voltageMap (mnm 2500 4800 5000))))

In the above example, given the assumption that mV implies a voltage unit of millivolts, the logic value T has an accepted range of values of 2.5 to 5.0 volts, and a nominal value of 4.8 volts.

See also:

weakJoined

weakJoined ::= '(' 'weakJoined'
	{ interfaceJoined | portRef } 
	')'

Used by:

interface mustJoin

Description:

WeakJoined is used to indicate that external connections may be made to any of the referenced ports,and that corresponding ports may not be used as feed-throughs. This statement is similar to interfaceJoined. Only ports defined in the local cluster may be referenced within weakJoined.

WeakJoined may contain nested interfaceJoined statements. Within the interface, a port may be referenced no more than once in interfaceJoined, mustJoin and weakJoined.

The portRef may refer to ports and not to portBundles.

Example:

(weakJoined
   (portRef gateTop)
   (portRef gateBottom))

This example declares that connections may be made to either gateTop or to gateBottom with the same effect, but the connection gateTop to gateBottom may not be used as a feed-through.

See also:

interfaceJoined

whiteSpace

Description:

A whiteSpace character is either a horizontal tab, line feed, carriage return, or space. These have ASCII codes of 9, 10, 13 and 32 respectively. Any token (identifier, integerToken, stringToken) not preceding a parenthesis '(' or ')', quote '"', or percent sign '%' within encodedCharacter must be followed by one or more whiteSpace characters. Further whiteSpace may be added between tokens without causing any change of interpretation.

The only situation where whiteSpace is significant (except for separating tokens) is the blank or tab characters within a stringToken.

Although not explicitly stated elsewhere, whiteSpace may also be added next to left or right parentheses (outside string tokens) without effect.

The first character after a sequence of whiteSpace characters not within a stringToken fully determines the type of token. A quote '"' begins a stringToken; ampersand '&', underscore '_' or alpha begins an identifier; a plus '+', minus '-', or digit begins an integerToken; a left parenthesis '(' indicates the start of a form, and a right parenthesis ')' indicates the end of a corresponding form. Parentheses may be considered to be single-character tokens.

Example:

(port  ref ...)

The white space between port and ref is required to avoid misinterpreting this as a keyword portRef.

See also:

$goal alpha encodedCharacter digit identifier integerToken specialCharacter

written

written ::= '(' 'written'
	timeStamp
	{ <author> | comment | <dataOrigin> | <program> | userData } 
	')'

Used by:

status

Description:

Written includes information relating to a specific item of EDIF data. It must include a timeStamp and may include program identification, human or organization identification, or location information to help the reader trace the origin of a particular part of the EDIF data.

Example:

(written
   (timeStamp (date 1986 11 30) (time 22 7 29))
   (author "J.  Knecht")
   (dataOrigin "Castalia")
   (program "Glasperlenspiel"))

This example shows a typical written statement. In this case, the EDIF data was created or modified on November 30, 1986. The person "J. Knecht" was involved in the process which occurred at location "Castalia". The program that created the new or modified data was called "Glasperlenspiel", and no version number was specified.

See also:

author dataOrigin program

xor

xor ::= '(' 'xor'
	{ booleanExpression } 
	')'

Used by:

booleanExpression

Description:

Performs a logical XOR operation between the expressions within booleanExpression. If an odd number of the expressions within booleanExpression evaluate to true, xor returns true.

If no booleanExpression is specified, the result is false.

Example:

(xor (true) (false) (false))

This example returns true.

See also:
