nameCaseSensitivity

nameCaseSensitivity ::= '(' 'nameCaseSensitivity'
	{ <clusterConfigurationNameCaseSensitive> | <clusterNameCaseSensitive> 
	| <designHierarchyNameCaseSensitive> | <designNameCaseSensitive> | 
	<documentationNameCaseSensitive> | <figureGroupNameCaseSensitive> | 
	<globalPortNameCaseSensitive> | <hotspotNameCaseSensitive> | 
	<implementationNameCaseSensitive> | <instanceNameCaseSensitive> | 
	<interconnectNameCaseSensitive> | <libraryNameCaseSensitive> | 
	<libraryObjectNameCaseSensitive> | <localPortGroupNameCaseSensitive> | 
	<pageNameCaseSensitive> | <portNameCaseSensitive> | 
	<propertyNameCaseSensitive> | <signalGroupNameCaseSensitive> | 
	<signalNameCaseSensitive> | <viewGroupNameCaseSensitive> | 
	<viewNameCaseSensitive> } 
	')'

Used by:

edifHeader libraryHeader

Description:

NameCaseSensitivity is used to define whether particular classes of names are to be compared on a case-sensitive or case-insensitive basis. This only applies to names that are defined as strings within nameInformation, and not to the identifier.

It is assumed that the precise meaning of "case sensitivity" is defined by the character definition, e.g. ascii, JIS X 0201.

The value defined in a libraryHeader overrides that defined in the edifHeader for objects within the library. The default is that names are case sensitive.

DesignNameCaseSensitive and libraryNameCaseSensitive may not appear in nameCaseSensitivity within libraryHeader because these names occur outside the scope of a library.

Example:

(nameCaseSensitivity
   (libraryNameCaseSensitive (false)))

This example shows that the names of libraries are to be compared on a case-insensitive basis.

nameInformation

nameDef

nameDef ::= identifier

Used by:

clusterConfigurationNameDef clusterNameDef connectivityRipperNameDef designHierarchyNameDef designNameDef diagramNameDef documentationNameDef edifNameDef figureGroupNameDef fontNameDef globalPortNameDef hotspotNameDef implementationNameDef instanceNameDef interconnectDelayNameDef interconnectNameDef libraryNameDef libraryObjectNameDef localPortGroupNameDef logicNameDef pageNameDef portDelayNameDef portLoadDelayNameDef portNameDef propertyNameDef sectionNameDef signalGroupNameDef signalNameDef symbolPortImplementationNameDef timingNameDef unitNameDef viewGroupNameDef viewNameDef

Description:

Every named object must have a defining occurrence as a nameDef. Subsequent references may be made to the object so named, using the same identifier in the role of a nameRef. Named constructs, i.e. constructs which have nameDef (directly or indirectly) as their first required item, provide a scope for any nested name definitions.

A named object is not fully defined, and may not be referenced explicitly, until the closing parenthesis of the definition.

All names in EDIF must be defined before use. The name should be unique for the scope of the defining construct, which is the next higher-named construct, and for its class, which is determined by the type of the nameDef.

There are no reserved names in EDIF. There is no semantic significance to the choice of identifier spelling within a nameDef, except for the structure established through corresponding nameRefs and the display of such names.

Example:

(cell TWOS_COMPLEMENT 
   (cellHeader 
      (nameInformation 
         (primaryName "2s-complement")))
   ...)

This example illustrates a cell defined to be TWOS_COMPLEMENT, a legal EDIF identifier, serving as an alias for the original illegal (in EDIF) name, "2s-complement".

nameDimension

nameDimension ::= '(' 'nameDimension'
	nameDimensionStructure
	{ <bitOrder> } 
	')'

Used by:

complementedName complexName

Description:

NameDimension is used to specify an ordered list of indices of a dimensioned object, such as a schematicBus. The indices specified in nameDimensionStructure can be names of other objects, integers, or an integer range called a sequence. If the indices are associated with bits, then the bitOrder should be specified. A bitOrder of lsbToMsb indicates that the first index is the least-significant bit and that the last index is the most-significant bit. A bitOrder of msbToLsb indicates that the first index is the most-significant bit and that the last index is the least-significant bit. If no bitOrder is specified, then no bit ordering of the indices is implied.

Multiple nameDimensions in the same list indicate that the object has multiple dimensions.

Example:

(nameInformation
   (primaryName "a[b,c,d][3:0]"
      (nameStructure
         (complexName "a"
            (nameDimension 
               (nameDimensionStructure "b" "c" "d"))
            (nameDimension
               (nameDimensionStructure
                  (sequence 3 0 (step 1) ))
               (bitOrder (msbToLsb)))))))

In the above example, a two-dimensional object named "a" is specified. The indices of the first dimension are "b", "c" and "d". The indices of the second dimension are 3, 2, 1 and 0, with 3 being the most-significant bit and 0 the least-significant bit. 

(nameInformation
   (primaryName "a[b[3:0],c[3:0],d[3:0]]"
      (nameStructure
         (complexName "a"
            (nameDimension
            (nameDimensionStructure
               (complexName "b"
                  (nameDimension
                     (nameDimensionStructure
                        (sequence 3 0 (step 1) ))
                     (bitOrder (msbToLsb))))
               (complexName "c"
                  (nameDimension
                     (nameDimensionStructure
                        (sequence 3 0 (step 1) ))
                     (bitOrder (msbToLsb))))
               (complexName "d"
                  (nameDimension
                     (nameDimensionStructure
                        (sequence 3 0 (step 1) ))
                     (bitOrder (msbToLsb))))))))))

In this example, a one-dimensional object named "a" is specified. It has indices of "b", "c" and "d". Each of these indices is a one-dimensional object name with indices of 3, 2, 1 and 0. In the original system "b", "c" and "d" are related to bits, with 3 being the most-significant bit and 0 the least-significant bit. Note that it is possible that the name in the first example is a different way of specifying the name represented in the second example.

See also:

namePartSeparator

namePartSeparator ::= '(' 'namePartSeparator'
	stringToken
	')'

Used by:

complementedName complementedNamePart complexName

Description:

A namePartSeparator is one or more characters which is used in the original system to separate parts of a complex name or complemented name. EDIF associates no semantics with these characters, only that the original system knows that they are part of the original name only as a name part separator. Although the original system may imply additional meaning to the separator, EDIF at this time does not.

Example:

(nameInformation
   (primaryName "clock&enable"
      (nameStructure
         (complexName "clock"
              (namePartSeparator "&" )
         "enable" ))))

Here in the originalName clock&enable, the character "&" separates the name parts "clock" and "enable".

See also:

complementedNamePart nameDimension simpleName

nameRef

nameRef ::= identifier

Used by:

clusterConfigurationNameRef clusterNameRef connectivityRipperNameRef figureGroupNameRef fontNameRef globalPortNameRef hotspotNameRef implementationNameRef instanceNameRef interconnectDelayNameRef interconnectNameRef libraryNameRef libraryObjectNameRef localPortGroupNameRef logicNameRef pageNameRef portDelayNameRef portLoadDelayNameRef portNameRef propertyNameRef signalGroupNameRef signalNameRef symbolPortImplementationNameRef timingNameRef unitNameRef viewGroupNameRef viewNameRef

Description:

A nameRef always corresponds to a previously-defined nameDef of the same class and within the same scope. The class of the name is indicated by the prefix to the category, such as viewNameRef or portNameRef.

The scope of a name is defined for each nameDef.

Certain reference mechanisms such as cellRef and portRef explicitly identify the required name class, and may access an indirect scope by including a nested reference.

Example:

(permutable (portRef p1) (portRef p2) (portRef p3))

The names p1, p2 and p3 are references to three previously-defined ports named p1, p2 and p3.

nameStructure

nameStructure ::= '(' 'nameStructure'
	( simpleName | complexName | complementedName )
	')'

Used by:

nameAlias primaryName

Description:

Many systems use special characters and sub-strings embedded within an object name to indicate information about the object, e.g. logical complement, boolean relationships, dimensionality, bit ranges, indices, etc. NameStructure is used to specify in detail the structural parts of a name without the use of special characters. NameStructure is also used to apply a certain semantic meaning to each of the name's parts.

NameStructure should be used if the sending system uses the name structure to specify the structure of the design object. For example, a schematicBus might have a name in the original system "DATA(a, b, c)", which implies that the bus "DATA" contains the signals "a","b" and "c". The characters '(', ')' and ',' are used to specify structure. This name should be specified in EDIF as a complexName.

Suppose a signal name "a" in the original system contains no structural information. This should be specified in EDIF as an originalName with no nameStructure. A name such as "~a", where the character '~' implies complement in the original system, should be specified in EDIF as a complementedName within nameStructure.

Where EDIF has provided syntax for representing the semantics implied by special characters, the special characters should be represented by the appropriate EDIF syntax.

When reading EDIF, a translator should re-assemble the name in the receiving system using the naming rules of that system. For example, a bus name "~DATA[0:3]" might be translated to "NDATA(0-3)".

There are no rules in EDIF about the uniqueness of a nameStructure specification, because the scope of nameStructure is dependent on the originating system.

Examples:

(nameInformation
   (primaryName "B1"
      (nameStructure
         (complexName "B"
            (nameDimension 
               (nameDimensionStructure 1))))))

In this first example, the receiving system may use the simpleName B and the index value 1 to generate a name according to its own conventions, e.g. "B(1)" or "B1". 

(nameInformation
   (primaryName "~(a.~b)[m,d[0:3],n]"
      (nameStructure
         (complementedName 
            "a"
            (namePartSeparator "." )
            (complementedNamePart "b" )
            (nameDimension  
               (nameDimensionStructure 
                  "m"
                  (complexName "d"
                     (nameDimension
                        (nameDimensionStructure
                           (sequence 0 3))))
                  "n"))))))

In this second example, the receiving system might map this name to ".NOT.(a.AND..NOT.b)[m,d0,d1,d2,d3,n]", assuming that the translator maps the namePartSeparator "." to ".AND.". 

(nameInformation
   (primaryName "a[1,5,7][0:8:2]"
      (nameStructure
         (complexName "a"
            (nameDimension 
               (nameDimensionStructure 1 5 7))
              (nameDimension 
               (nameDimensionStructure
                      (sequence 0 8 (step 2))))))))

In this third example, the specification indicates that the object is two dimensional.

See also:

originalName

nonPermutable

nonPermutable ::= '(' 'nonPermutable'
	{ permutable | portRef } 
	')'

Used by:

permutable

Description:

NonPermutable is used to describe ports or groups of ports which cannot be interchanged. Used in conjunction, the nonPermutable and permutable constructs define a permutability tree structure of ports within the interface. A port may be referenced no more than once within a permutable or nonPermutable in an interface. The order of portRefs is significant, as in the schematic below.

References to portBundles are treated as if they were expanded to individual members. In the context of a permutable construct, corresponding ports may be exchanged as a whole or not at all; partial exchanges are not permitted.

nonPermutable schematic

Example:

(permutable
   (nonPermutable (portRef A) (portRef B))
   (nonPermutable (portRef C) (portRef D)))

The example states that the ports A and B are not permutable, and also that the ports C and D are not permutable. However, the ports A and C may be permuted as long as the ports B and D are permuted at the same time. This structure could be appropriate for the previously-illustrated schematic.

See also:

interface port

occurrenceAnnotate

occurrenceAnnotate ::= '(' 'occurrenceAnnotate'
	( extendInstanceDef | extendInstanceMemberDef )
	{ cellPropertyOverride | clusterPropertyOverride | comment | <designator> 
	| instancePropertyOverride | interconnectAnnotate | leafOccurrenceAnnotate 
	| occurrenceAnnotate | pageAnnotate | portAnnotate | property | 
	signalAnnotate | signalGroupAnnotate | timing | viewPropertyOverride } 
	')'

Used by:

occurrenceAnnotate occurrenceHierarchyAnnotate

Description:

OccurrenceAnnotate introduces annotation data for an instance, or in the case of a wide instance an instance member, and all of the instances beneath it in the instance (occurrence) hierarchy.

ExtendInstanceDef or extendInstanceMemberDef refers to the instance or instance member to which this annotation applies. This identifies a cluster which is being instantiated. If further annotation is to be given for instances below this one, then nested occurrenceAnnotate or leafOccurrenceAnnotate forms are used to give their annotation. Nested annotation must be consistent with the hierarchy configuration.

Only one occurrenceAnnotate is allowed per instance.

Example:

(occurrenceAnnotate hier1
   (leafOccurrenceAnnotate elem1
      (designator "U2")
      (portAnnotate &1 ...
         (designator "11"))
      (portAnnotate &2 ...
         (designator "12"))
      (portAnnotate &3 ...
         (designator "13")))
   (leafOccurrenceAnnotate elem2
      (designator "U2")
      (portAnnotate &1 ...
         (designator "6"))
      (portAnnotate &2 ...
         (designator "7"))
      (portAnnotate &3 ...
         (designator "8"))))

In this example, hier1 is a hierarchical instance. Within the selected view of the cluster instantiated by hier1, there are two instances: elem1 and elem2. Each of these has a designator and port annotation data.

origin ::= '(' 'origin'
	pointValue
	')'

Description:

Origin is used to specify the translation point of an object when it is transformed. Translation of an object is always the last operation performed when transforming an object.

(annotate "U12"

      (figureGroupOverride text 
         (displayAttributes 
            (verticalJustification (bottomJustify))
            (horizontalJustification (leftJustify))))
      (transform (rotation 270)
         (origin (pt 4 6)))))

The second example specifies that the string "U12" is to be displayed such that the lower left of the text (below and left of the "U"), is at point (4, 6).
