k3Build

k3Build ::= '(' 'k3Build'
	k1KeywordNameRef
	{ comment | k2Actual | k2Literal | k3Build | k3ForEach } 
	')'

Used by:

k3Build k3ForEach

Description:

K3Build is used within the context of a k3KeywordDefine to generate non- primitive output. It contains a k1KeywordNameRef, which is the name of an existing (or previously-defined) keyword. K3Build expands into a form with k1KeywordNameRef as its keyword, and with each component of the k3Build replaced by the result of generating the enclosed constructs in the order specified. The comments generate nothing, but provide documentation about the purpose or use of the keyword definition.The k3Build construct can use embedded k3ForEach constructs to process lists of arbitrary length.

Example:

(k3KeywordDefine inport
   (k3KeywordParameters
      (k3Formal name (k3Collector))
      (k3Formal load (k3Collector)))
   (k3Generate
      (k3ForEach (k3FormalList name load)
         (k3Build port (k2Actual name)
            (k3Build inputPort)
            (k3Build acLoad (k2Actual load))))))

This example defines a keyword which accepts any number of pairs consisting of a port name and a corresponding load value, such as

(inport p1 15 p2 20 p3 45)

which generates the following: 

(port p1 (inputPort) (acLoad 15))
(port p2 (inputPort) (acLoad 20))
(port p3 (inputPort) (acLoad 45))

See also:

k2Build

k3Collector

k3Collector ::= '(' 'k3Collector'
	')'

Used by:

k3Formal

Description:

K3Collector allows a k3Formal parameter to be bound to a list of values, as opposed to a single value.

If a k3Formal parameter contains a nested k3Collector, then it will be bound to all input arguments that are in excess of the number of k3Formal parameters defined for the keyword. Any k3Formal parameter following a k3Collector parameter must also be a k3Collector parameter. If there is more than one k3Collector parameter, then the extra values will be evenly distributed among them in turn. The number of actual forms and tokens bound as a list to each k3Collector parameter must be the same.

Example:

(k3KeywordDefine EG
   (k3KeywordParameters
      (k3Formal a (k2Required))
      (k3Formal b (k2Required))
      (k3Formal c (k3Collector)) ...)
   ...)

See also:

k3Build k3ForEach k2Optional

k3ForEach

k3ForEach ::= '(' 'k3ForEach'
	( k2FormalNameRef | k3FormalList )
	{ comment | k2Actual | k2Literal | k3Build | k3ForEach } 
	')'

Used by:

k3Build k3ForEach k3Generate

Description:

K3ForEach is a looping construct that is used to build forms iteratively. It is used in conjunction with the keyword builder constructs k3Build and k3Generate. The builders specified within the k3ForEach will be expanded as long as the list of values bound to the k3Formal parameter (or parameters) specified in the k3ForEach is not exhausted. In other words, the builders contained within k3ForEach will be expanded for each value that is bound to the specified k3Formal parameters. K3ForEach is used to generate forms that use k3Formal parameters which are defined as k3Collector parameters.

Any k2Actual statements within k3ForEach which reference the same formal parameter should expand to a single value on each iteration.

Example:

(k3KeywordDefine inport
   (k3KeywordParameters
      (k3Formal name (k3Collector))
      (k3Formal load (k3Collector)))
   (k3Generate
      (k3ForEach (k3FormalList name load)
         (k3Build port (k2Actual name)
            (k3Build inputPort)
            (k3Build acLoad (k2Actual load))))))

This example defines a keyword that will create several input port declarations and specify an acLoad value for each. This could later be used in a statement such as:

(inport portA 12 portB 15 portC 6)

The name inport is not a native EDIF keyword and would not be legal without the appropriate definition.

This would generate: 

(port portA (inputPort) (acLoad 12))
(port portB (inputPort) (acLoad 15))
(port portC (inputPort) (acLoad  6))

See also:

k3Collector

k3FormalList

k3FormalList ::= '(' 'k3FormalList'
	{ k2FormalNameRef } 
	')'

Used by:

k3ForEach

Description:

K3FormalList contains a set of formal parameter references which are used to control the iterations of the k3ForEach form. Such iteration should step through the collected values of each referenced formal parameter in parallel, each of which should be bound to the same number of actual values.

Example:

(k3KeywordParameters
   (k3Formal name (k3Collector))
   (k3Formal load (k3Collector)))
(k3Generate
   (k3ForEach (k3FormalList name load)
      (k3Build port (k2Actual name)
         (k3Build inputPort)
         (k3Build acLoad (k2Actual load)))))

This example illustrates the collection and use of a series of port name and acLoad value pairs.

See also:

k3Build k3Generate

k3Generate

k3Generate ::= '(' 'k3Generate'
	{ comment | k2Actual | k2Build | k2Literal | k3ForEach } 
	')'

Used by:

k3KeywordDefine

Description:

K3Generate is used to specify the expansion of a form which references a defined keyword. Since this construct contains an arbitrary number of builders, the use of a k3KeywordDefine can generate more than one form. In such cases it should not be used as a positional item within the enclosing construct.

Example:

(k3KeywordDefine inport
   (k3KeywordParameters
      (k3Formal name (k3Collector))
      (k3Formal load (k3Collector)))
   (k3Generate
      (k3ForEach (k3FormalList name load)
         (k3Build port (k2Actual name)
            (k3Build inputPort)
            (k3Build acLoad (k2Actual load))))))

This example shows the use of k3ForEach within a k3Generate keyword definition. A typical use could be: (inport IN1 10 IN2 20), which would generate: 

(port IN1 (inputPort) (acLoad 10))
(port IN2 (inputPort) (acLoad 20))

See also:

k2Actual k3Build k3ForEach

leaf

leaf ::= '(' 'leaf'
	')'

Used by:

clusterConfiguration

Description:

Leaf specifies that the cluster is to be treated as a leaf, i.e. the hierarchy expansion goes no further. This is an explicit decision to terminate the hierarchy at the cluster.

Example:

(cell A ...
   (cluster B ...
      (clusterConfiguration C (leaf))))

In this example, the clusterConfiguration C specifies that the hierarchy expansion of cluster B goes no further.

See also:

library

library ::= '(' 'library'
	libraryNameDef
	libraryHeader
	{ cell | comment | geometryMacro | pageBorderTemplate | 
	pageTitleBlockTemplate | schematicFigureMacro | 
	schematicGlobalPortTemplate | schematicInterconnectTerminatorTemplate | 
	schematicJunctionTemplate | schematicMasterPortTemplate | 
	schematicOffPageConnectorTemplate | schematicOnPageConnectorTemplate 
	| schematicRipperTemplate | schematicSymbolBorderTemplate | 
	schematicSymbolPortTemplate | userData } 
	')'

Used by:

edif

Description:

Library is a collection of EDIF design information, grouped according to some set of common characteristics. This grouping is arbitrary except for the technology information within libraryHeader, which is shared by all objects in the library. Libraries are often grouped by technology definition (such as CMOS), but the same technology could be defined in more than one library by repeating the information in technology.

A library that is external to the EDIF data is described using the external form in the edif form.

The objects to be found in a library consist of cells, which may be hierarchical, and definitions of templates. These objects all share the same name space. It is not possible, for example, to have a schematicMasterPortTemplate and a schematicSymbolPortTemplate with the same name in the same library.

Example:

(edif HYBRID_DESIGNS
   (edifVersion 3 0 0)
   (edifHeader ...)
   (library CMOS2M
      (libraryHeader (edifLevel 0)
         (nameCaseSensitivity)
         (technology ...))
      (cell MUX ...)
      (cell FFT ...)))

This example shows the definition of a library named CMOS2M which contains technology and the definitions of cells MUX and FFT.

See also:

external

loadDelay

loadDelay ::= '(' 'loadDelay'
	acLoadFactorTime
	acLoadFactorCapacitance
	')'

Used by:

portLoadDelay portLoadDelayOverride

Description:

LoadDelay is used to specify a delay in propagating a signal. AcLoadFactorTime and acLoadFactorCapacitance specify the amount of delay per load capacitance as specified by the acLoad on each of the ports connected to the driving port. None of these values may be negative. AcLoadFactorCapacitance will typically be 1.

Example:

(loadDelay (e 2 -1) 1)

The first example describes a load-dependent delay of 0.2 time units per unit load capacitance. 

(port P1 (bidirectionalPort)
   (portDelay PD1 (measured) (delay 25))
   (portLoadDelay PLD1 (measured)
      (loadDelay 2 1)
      (transition D U)))

The second example specifies a measured delay of 25 time units plus 2 time units per unit acLoad of load-dependent delay. This occurs on a transition from D to U of the port named P1.

See also:

acLoad delay setTime setCapacitance

localPortGroup

localPortGroup ::= '(' 'localPortGroup'
	localPortGroupNameDef
	portList
	{ comment | <nameInformation> | property | userData } 
	')'

Used by:

connectivityStructure page

Description:

LocalPortGroup provides a mechanism to describe structured ports which have not been defined in the interface, but which are required to support structural connectivity. LocalPortGroup is a structuring mechanism only and does not itself define the ports or modify the interface in any way. A localPortGroup may be referenced, for example, from schematicMasterPortImplementation.

A localPortGroup is defined as an ordered list of master ports and master port bundles, described in portList. There must be at least two portRefs in the portList. PortList may only reference master ports and master port bundles and not other localPortGroups.

A port or portBundle may be directly referenced by zero or more localPortGroups in the same page or connectivityStructure. A localPortGroup may not reference a port or portBundle more than once, either directly or indirectly.

It is not permitted to form a localPortGroup whose portList is identical to the portList of an existing portBundle. However, it is permitted to form two localPortGroups that have identical portLists.

Example:

...
(interface
   (interfaceUnits)
   (port a ...)
   (port b0 ...)
   (port b1 ...)
   (port b2 ...)
   (port b3 ...)
   (port b4 ...)
   ...
   (port b31 ...)
   (portBundle B_BUN
      (portList
         (portRef b0)
         (portRef b1)
         (portRef b2)
         ...
         (portRef b30)
         (portRef b31)))...)
...
(schematicImplementation
   (page P1
      (pageHeader ...)
      ...
      (localPortGroup tempGroup
         (portList
            (portRef a)
            (portRef b2)
            (portRef b3)))
      ...
      (schematicMasterPortImplementation PIN3
         (schematicMasterPortTemplateRef INPORT
            (libraryRef SCHEMLIB))
         (localPortGroupRef tempGroup)
            (transform ...)...)...)...)

In this example the interface contains the port a, ports b0 through b31 and a portBundle B_BUN grouping b0 through b31. The schematicMasterPortImplementation references ports a, b2 and b3. This local grouping is represented by a localPortGroup.

See also:
