Chapter 5

Design hierarchy configuration

 

This chapter describes how an occurrence hierarchy is configured in EDIF. The model for configuration can be found in the hierarchy_model and the design_hierarchy_model .

5.1 Problem statement

In EDIF Version 2 0 0, a cell may contain many views of the same or different types. Each view is structured as an interface (containing ports) and an optional contents (containing nets and instances of other views). Since each instance in a contents references exactly one view and since that view has at most one contents, the tree structure of a design is unambiguous.

In EDIF Version 3 0 0 instances are not of views but rather of clusters - which contain one interface but may have multiple views. Therefore, for a given design to have an unambiguous tree structure, it is necessary to be able to specify for each instance which view is to be used. Furthermore, it is necessary to be able to specify alternative configurations for instances so that different design trees may be represented.

In addition to choosing specific configurations of specific views it may also be necessary to specify that, in a particular configuration, a given instance may be a leaf and use none of the views of its cluster. Finally, not all configuration information may be available for a given design transfer. Therefore a mechanism for explicitly having unconfigured instances is needed.

5.2 Solution

As mentioned in section 2.3, EDIF Version 3 0 0 introduces the notion of cluster which consists of an interface definition and the cell_representations sharing that interface. The cell definition may contain many clusters. Instances are created by instantiating clusters, rather than instantiating specific views. Hence, the use of cluster provides the beginnings of a configuration mechanism.

In addition, EDIF Version 3 0 0 has added the concepts of cluster_configuration and instance_configuration to support the configuration mechanism. A cluster may contain many cluster_configurations, each of which describes how to continue expanding the hierarchy. A cluster_configuration can be either an expandable_cluster_configuration or a leaf_configuration.

An expandable_cluster_configuration identifies a view for the further expansion of the hierarchy. The chosen view must belong to the containing cluster of the expandable_cluster_configuration. Each instance defined within the chosen view must be either configured or unconfigured. To configure an instance, it is necessary to specify an instance_configuration. An instance_configuration selects a valid cluster_configuration for the configured instance. The chosen cluster_configuration must be defined in the instantiated cluster of the configured instance. To unconfigure an instance, it is necessary to state explicitly that an instance is required to be unconfigured. Thus, an expandable_cluster_configuration may contain many unconfigured_instances and many instance_configurations. In a given expansion, an instance may be configured at most once.

If an instance has an instance_configuration which references a leaf_configuration, there is no further structure in the design tree below that instance.

A design_hierarchy is defined by selecting the top cluster_configuration. A design may contain many design hierarchies. For each design_hierarchy, the chosen cluster_configuration must be defined in the cluster_interface of the top_cell of the design.
