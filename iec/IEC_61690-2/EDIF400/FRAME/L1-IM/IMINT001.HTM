3 Extensions to Level 0

The basic EDIF Level 0 description is used for sending static descriptions of electronic design data. The bulk of normal design transfer is expected to be done in Level 0 EDIF. However, EDIF Level 0 cannot support parameterization of cells. In addition, it does not allow users to define replication of subcircuits or make the existence of subcircuits dependent on some conditions. In this chapter, the basic concepts are extended to include these new features.

3.1 Clusters

A cluster defines a cluster_interface and groups together views or symbols which share this common interface. A cluster_interface specifies objects which can be seen and relationships which must hold for all views and symbols within a cluster. It includes definitions of master_ports and master_port_bundles. In Level 1, parameters are added to the cluster_interface so that objects defined within a cluster can be parameterized. Parameters may be declared to be of type boolean, integer, number or string. They may be given default values of the appropriate type, in which case parameter assignment during instantiation is optional; parameters without default values must have a value assigned to them on instantiation.

3.2 Ports

Ports are defined in the cluster_interface. They represent the only places where a connection can be made to a cell. In Level 1, parameters are introduced in the cluster_interface. Hence, it is possible to parameterize the master_ports defined within the cluster_interface. The width of a master_port is no longer restricted to be one and can be varied by giving an associated width expression. The width expression is an integer_expression which may reference parameters defined in the containing cluster_interface. A master_port has a port_name_generator expression which is used to generate the port_name of each port occurrence that will be generated during design expansion.

3.3 Views

A view is defined within a cluster and may contain instances, signals, signal_groups, nets or busses. At present, the model has completely described connectivity views, schematic views and PCB/MCM views. In Level 1, the concept of frame is introduced. A frame is defined within a connectivity view or a schematic view. It describes a circuit which may be repeated a number of times (i.e. for_frame) or conditionally included (i.e. if_frame) during expansion of the design. The contents of a frame may include instances, frame_signals and frame_signal_groups.

3.4 Instances

An instance allows a cluster to be referenced from within a view to create the instance hierarchy of a design. Each instance may represent a multiplicity of expanded instance elements, as determined by a width expression. In Level 1, parameters are defined in the cluster_interface. Thus, when an instance is used, it is necessary to be able to assign values to parameters defined in the interface of the instantiated cluster. This is achieved by using parameter_assign. An integer width expression is used to declare the number of instance elements that will be generated during design expansion.

In addition, instance has been extended to include an instance_name_generator. This is a string_expression which may reference parameters defined in the cluster_interface of the containing view. Consider the following example of using an instance_name_generator. Assume that an engineer has defined a technology parameter which has a string value of "cmos". The engineer can then tag the instance name with the result of the technology parameter. Suppose the circuit has an instance of a gate and that instance has an instance_name_generator expression which is a concatenation of the technology parameter and the gate name "NAND". The instance name of that gate will be "cmosNAND" after expansion.

Similarly, the instance_name_generator supports the introduction of frames in Level 1. An instance is subject to repetition when it is defined inside a for_frame. The instance_name_generator provides a mechanism for controlling the name of each instance element after the expansion of a for_frame.

3.5 Signals

A signal is defined as an object which incorporates all the master_ports, instance_ports and global_ports which are electrically common at a given level of hierarchy. Since parameters are introduced in the cluster_interface in Level 1, it is possible to parameterize signals defined within a parameterized cluster. The width of a signal is no longer restricted to be one and can be varied according to its associated width expression. The width expression is an integer_expression which may reference parameters defined in the containing cluster_interface. Each joined instance_port will specify a connected_signal_index_generator expression which, on evaluation, determines the manner in which the individual bits of an expanded instance_port connect to the expanded signal.

In addition, a signal is classified as either a mergeable_signal or a non_mergeable_signal in Level 1 EDIF. A mergeable_signal has an associated connectivity_tag_generator expression. Connectivity_tag_generators are compared after evaluation to determine which mergeable_signals or frame_mergeable_signals within an internal_cell_representation are to be merged.
