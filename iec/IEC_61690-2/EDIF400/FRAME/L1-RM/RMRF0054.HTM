(See also similar constraint in: pcbNonSpecificLayoutShape, pcbPad)

2. The following constraint applies to this context: All contexts

(See also similar constraint in: pcbNonSpecificLayoutShape, pcbPad)

3. The following constraint applies to this context: All contexts

Description:

Defines a connected set of lines and arcs which are applied using real material, or are cut out of other material that has already been applied to the bare board, or both.

The trace and the clearance geometry must be open shapes, e.g. they cannot be rectangular.

Traces are straightforward features on the bare board that often need to be manipulated by automatic routers.

The trace does not necessarily have to be made from conductive material, e.g. it could be part of the silkscreen information.

Example:

(pcbLayoutFeature LF1
   (pcbTrace
      (pcbFabricateFigure
         (pcbContributesToFabrication
            (pcbSimpleFabricateFigureCollectorRef 
               FC1))
         (pcbPhysicalFigure POWER_NETS
            (geometryElementSet
               (path
                  (pointList
                     (pt -8509000 6432550)
                     (pt -8509000 8382000)
                     (pt -6096000 8382000))))))
      (pcbClearanceGeometry)))

permutable

permutable ::= '(' 'permutable'
	{ nonPermutable | permutable | portRef } 
	')'

Used by:

*interface *nonPermutable *permutable

Similar Keywords:

pcbElectricalPartFunctionNonPermutable pcbElectricalPartFunctionPermutable pcbElectricalTerminalNonPermutable pcbElectricalTerminalPermutable

Constraints:

1. The following constraint applies to this context: All contexts
The number of portRefs used inside permutable or nonPermutable constructs should be equal when they are nested in further permutable or nonPermutable constructs.
(See also similar constraint in: nonPermutable)

2. The following constraint applies to this context: All contexts
A port can be referenced at most once by any permutable or nonPermutable constructs in an interface.
(See also similar constraint in: nonPermutable)

Description:

Permutable is used to describe a relationship in which ports are interchangeable, for example, the input ports of an AND gate. The ports referenced within permutable must be individual not bundled (see constraints under portNameRef). Permutable may also contain permutable and nonPermutable constructs. Permutable may be nested with NonPermutable to specify complex relationships between ports defined in the local cluster (master ports). This explicitly provides a degree of freedom for the external routing of this view.

Nested nonPermutable structures may be exchanged as a whole, but not partially.

Nested permutable example

Example:

(port A (inputPort))
(port B (inputPort))
(permutable (portRef A) (portRef B))

This states that connections to ports A and B may be interchanged during routing of this view without affecting the logical operation of the view.

pixelPattern

pixelPattern ::= '(' 'pixelPattern'
	rowSize
	{ pixelRow } 
	')'

Used by:

!borderPattern !fillPattern

Description:

PixelPattern defines a pattern of pixels. It is a two-dimensional array of pixels. RowSize defines the number of pixels in each row of pixels. PixelRow defines the status of each pixel in a row. Use one pixelRow construct for each row of pixels required. The first pixelRow defines the status of the uppermost row of pixels.

Example:

(fillPattern
   (pixelPattern 1
      (pixelRow (true))))

In this example, a pixel pattern is defined consisting of a single pixel which is on. 

(fillPattern
   (pixelPattern 3
      (pixelRow (true) (false) (false))
      (pixelRow (false) (true) (false))))

In this example, a pixel pattern is defined consisting of a two-by-three array of pixels, creating the pattern shown below, which assumes that the foreground color is black and the background color is white.
