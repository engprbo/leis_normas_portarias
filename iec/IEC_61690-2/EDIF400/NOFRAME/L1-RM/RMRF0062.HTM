Description:

A signal is a named object which lists ALL the ports, master, instance and global, which are electrically common at a given level of hierarchy. A signal definition applies to an entire view.

A signal is always one bit wide in Level 0.

The signals define all the connectivity at a given level of hierarchy within a view.

      (portInstanceRef P1 (instanceRef I1))))

In this example, the signal SIG1 joins the master port MP1 and the port P1 of instance I1.

signalGroup

signalGroup ::= '(' 'signalGroup'
	signalGroupNameDef
	signalList
	{ <nameInformation> | property } 
	')'

Used by:

*logicalConnectivity

Similar Keywords:

extendSignalGroupDef signal signalGroupAnnotate signalGroupNameCaseSensitive signalGroupNameRef signalGroupRef

Constraints:

1. The following constraint applies to this context: All contexts
No two signal groups in the same context should have the same list of members

2. This construct is illegal in this context: external

Description:

A signalGroup is a named object which provides a grouping mechanism for signals. This provides a basis for the structured connectivity established by busses by allowing a hierarchical grouping mechanism for signals.

A signalGroup does not establish connectivity; it has no signalJoined.

A signalGroup is defined in terms of an ordered list of one or more signals or signalGroups. No two signalGroups may have the same list of members, although when flattened, two signalGroups may possibly resolve to the same ordered list of signals. Thus, different signalGroups will have different structure.

A signalGroup has a width that is equal to the sum of the widths of its constituent members.

The same signal or signal group may be referenced in the signalList of more than one signalGroup.

The same signal or signal group may be referenced more than once in a single signalGroup definition.

SignalGroups define their structure in terms of the signals and signalGroups that they reference. This structure is independent of the port ordering or port structure.

Example:

(signal OP_0 ...)
(signal OP_1 ...)
(signal OP_2 ...)
(signal OP_3 ...)
(signalGroup OP_0_1 
   (signalList (signalRef OP_0) (signalRef OP_1)))
(signalGroup OP_2_3 
   (signalList (signalRef OP_2) (signalRef OP_3)))
(signalGroup OP 
   (signalList (signalRef OP_0_1) (signalRef OP_2_3)))

In this example, four signals are defined and then grouped. The first two, OP_0 and OP_1, are grouped into one signalGroup, OP_0_1. The second two, OP_2 and OP_3, are grouped into another signalGroup, OP_2_3. Finally a signalGroup OP is defined as a grouping of the previously-defined signalGroups OP_0_1 and OP_2_3.

signalIndexValue

signalIndexValue ::= '(' 'signalIndexValue'
	')'

Used by:

integerExpression

Similar Keywords:

indexValue signal

Constraints:

1. The following constraint applies to this context: All contexts
A signalIndexValue can only be used directly or indirectly in the context of a connectivityTagGenerator.

Description:

SignalIndexValue returns the value of a signal index when a wide signal is expanded. This may be used, for example, in the definition of connectivityTagGenerator.

For an signal of signal width N, the signalIndexValue will return values 0 through N-1.

Example:

(signal SIG1 (signalJoined ...)
   (signalWidth 4)
   (connectivityTagGenerator
      (stringConcatenate "SIG1_"
         (decimalToString (signalIndexValue)))))

In this example, the connectivity tags for the four signals generated will be "SIG1_0", "SIG1_1", "SIG1_2" and "SIG1_3".

signalWidth

signalWidth ::= '(' 'signalWidth'
	integerExpression
	')'

Used by:

<signal

Similar Keywords:

width

Description:

Specifies the number of one-bit signals that will be generated during the design hierarchy expansion. The signal width may be dependent on parameter values. If signalWidth is not specified, a single one-bit signal will be generated.

Before expansion, the signal is regarded as an individual entity.

At Level 1, signals may have a width greater than one and this width may be expressed in terms of parameter values. The way that a wide signal is connected to a wide port is described under connectedSignalIndexGenerator.

When a signal is connected to a global port, the signal width must exactly match the global port width, i.e. the signal width must be one.

At Level 1, it is legal to reference a wide port from a wide signal. However, it is also legal to reference a member of a wide port from a scalar signal, even if the width of the port is not known. When parameters are used it is possible to determine the validity of the reference only after design hierarchy expansion.

Example:

(signalWidth (integerParameterRef dataWidth))

Here, the signalWidth is specified by the dataWidth parameter.

status

status ::= '(' 'status'
	{ comment | copyright | userData | written } 
	')'

Used by:

<cellHeader <clusterHeader <connectivityViewHeader <designHeader <documentationHeader <edifHeader <geometryMacroHeader <libraryHeader <pageHeader <pcbBareBoardTechnologyHeader <pcbDiePhysicalTemplateHeader <pcbDrawingTemplateHeader <pcbMaterialHeader <pcbMcmViewHeader <pcbMountablePackageHeader <pcbMountingMethodHeader <pcbPackageHeader <pcbPartHeader <pcbSubLayoutDefinitionHeader <pcbTemplateHeader <schematicSymbolHeader <schematicTemplateHeader <schematicViewHeader

Similar Keywords:

pcbAllocationSwapStatus

Description:

Status may appear in a variety of EDIF sections. Its primary purpose is to convey accounting and problem analysis information for the design. Status provides the information needed to trace back to the source of each piece of data, the human author or organization which owns the data, the program name, and the software revision used for creation of specific parts of the EDIF data.

Status applies to the immediately-enclosing form unless overridden by a lower-level status in an enclosed named form. For example, a status within a given library applies to the whole of that library unless a cell within the library has a status, in which case the cell's status applies to that cell. Also, for example, if any cell in a library is modified, then that library should be considered to have changed.

Several written statements may be used to record a history of modifications.

Example:

(library L1
   (libraryHeader
      (edifLevel 0)
      (nameCaseSensitivity)
      (technology ...)
      (status
         (written
            (timeStamp (date 1987 6 1) 
               (time 12 0 0))
            (program "EDIF_$Schem_out"))))
   (cell C1 
      (cellHeader
         (status
            (written
               (timeStamp (date 1987 5 11) 
                  (time 3 12 0))
               (program 
                  "EDIF_$IncrementalSchem_out"))))
      ...))

In the above example, the information contained within the library L1 was last modified on June 1, 1987, at 12:00:00 UTC using the program EDIF_$Schem_out. The cell C1 within the library L1 was produced or modified on May 11, 1987, at 3:12:00 UTC, using the program EDIF_$IncrementalSchem_out.
