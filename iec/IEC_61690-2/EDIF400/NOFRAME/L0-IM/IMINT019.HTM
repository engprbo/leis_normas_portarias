24 Assembled boards

The model of assembled_board can be found in the pcb_assembled_board_model schema. An assembled_board consists of one bare_board and a collection of component_implementations, embedded_component_implementations and assembled_physical_nets. A bare_board is the instantiation of a bare_board_definition. Figure 24.1 shows the model of assembled_board.

Figure 24.1: The model of assembled_board

24.1 Component implementations

A component_implementation defines how a component (see section 23.1) is mounted or printed on a bare board. It specifies the footprint_instance onto which the component is mounted, or which realises the printed component. The referenced footprint_instance must be defined in the bare_board_definition (see chapter 20) that is instanced as the basis for the assembled_board. A component_implementation is divided into various categories, depending on the type of the implemented component. It can be a packaged_component_implementation, a die_component_implementation or a printed_component_implementation. A packaged_component_implementation is used to implement a packaged component (i.e. mechanical_component, packaged_connector_component, packaged_electrical_component, jumper_component). It describes how a component is mounted onto the bare board by specifying the mountable_package (see chapter 17) for the component. Similarly, a die_component_implementation is used to implement a die_electrical_component. It specifies the mountable_die_physical_template (see section 18.4) which is used to mount the die component onto a bare board. Finally, a printed_component_implementation is used to implement a printed component (i.e. printed_electrical_component, printed_connector_component). Figure 24.2 shows the model of component_implementation.

Figure 24.2: The model of component_implementation

24.2 Component terminal implementations

Component terminals are implemented by component_terminal_implementations. A component_terminal_implementation defines how a terminal of a component is mounted or printed on a bare board. It specifies the toeprint_padstack_instance onto which the component terminal is mounted, or which realises the printed component terminal. The referenced padstack_instance must be defined in the toeprint_instance which is part of the footprint_instance onto which the component is mounted or printed. Similar to component_implementation, a component_terminal_implementation is also divided into several categories. A packaged_component_terminal_implementation specifies how a mountable_package_terminal of the referenced mountable_package is connected to the bare board. A die_component_terminal_implementation specifies how a mountable_bond_pad of the referenced mountable_die_physical_template is connected to the bare board. Figure 24.3 shows the model of component_terminal_implementation.

Figure 24.3: The model of component_terminal_implementation

24.3 Embedded component implementations

An embedded_component_implementation defines how a component (see section 23.1) is realised as an embedded die (see chapter 21) on a bare board. It specifies an embedded_die which implements the component. The referenced embedded_die must be defined in the bare_board_definition (see chapter 20) that is instanced as the basis for the assembled_board.

24.4 Assembled physical nets

On an assembled_board, an assembled_physical_net describes the physical implementation of a component_signal (see section 23.2). It identifies the component_terminals that have actually been connected together by the assembled_physical_net. It also identifies the collection of instance_nets (in the bare_board) that have contributed to the implementation of the component_signal on the assembled_board. Figure 24.4 shows the model of assembled_physical_net.

Figure 24.4: The model of assembled_physical_net

As stated in section 23.2, the component_signals describe the desired state of the board, whereas the assembled_physical_nets describe the connectivity as realised by the physical board. The assembled_board contains a collection of assembled_physical_nets which can be either all analysed or all non-analysed. An analysed_assembled_physical_net has been analysed by the sending system; whereas a non_analysed_assembled_physical_net has not been checked by the sending system. An analysed_assembled_physical_net determines whether or not it implements a component_signal correctly. If it is a correct_assembled_physical_net, the set of component_terminals joined by an assembled_physical_net must agree with the ones joined by its implemented component_signal. On the other hand, if it is an incorrect_assembled_physical_net, it may short component_signals together, or be incorrect for another reason (e.g. incomplete). A shorting_assembled_physical_net is found to shorting together the conductive material that implements one or more component_signals, and possibly other conductive material that implements no component signal (e.g. shielding).

24.5 Jumper connections

An assembled_physical_net may include a set of jumper_connections and/or jumper_components which represent physical connections that cannot or must not be represented by geometry belonging to a particular layer of the bare board. Sometimes a connection is designed to be completed after bare board manufacture of a printed circuit board, by means of a slip-on connection between component pins, or by soldering a wire between terminals. A jumper_connection is a discrete wire (i.e. discrete_jumper_wire) or a wirebond (i.e. jumper_wirebond) that completes a connection in an assembled_board, somewhere in the Z-direction from the plane of the board. It must specify at least two jumper_points which are the "landing_places" of a jumper_connection. A jumper_point can be either a component_terminal or a padstack_instance. The referenced padstack_instance must be defined within the bare board, within a toeprint_instance on the bare board, or within a toeprint_instance on a footprint_instance on the bare board.
