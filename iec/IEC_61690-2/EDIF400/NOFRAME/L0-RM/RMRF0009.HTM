horizontalJustification

horizontalJustification ::= '(' 'horizontalJustification'
	( leftJustify | centerJustify | rightJustify )
	')'

Used by:

<displayAttributes <pcbDimensionDrawingAttributeOverride <pcbDrawingAttributeDefault <pcbDrawingTextDrawingAttributeOverride <pcbGeometricAttributeDefault <pcbTextAttributeOverride

Similar Keywords:

horizontal

Description:

HorizontalJustification defines how rendered text is horizontally positioned relative to the origin given in the display defined for the text. To justify text, the text bounding box is computed. Prior to rotation, the text is horizontally positioned so the X origin is at the left edge, center or right edge of the bounding box for leftJustify, centerJustify or rightJustify respectively.

If horizontalJustification is not specified, leftJustify is assumed.

Example:

(figureGroup small_text
   (displayAttributes 
      (color 0 0 50) 
      (fontRef courier)
      (horizontalJustification (leftJustify))
      (verticalJustification (middleJustify))
      (textHeight 160)) ...)

hotspot

hotspot ::= '(' 'hotspot'
	pointValue
	{ <hotspotConnectDirection> | <hotspotNameDisplay> | 
	<nameInformation> | <schematicWireAffinity> } 
	')'

Used by:

!ripperHotspot !schematicGlobalPortTemplate !schematicInterconnectTerminatorTemplate !schematicJunctionTemplate !schematicMasterPortTemplate !schematicOffPageConnectorTemplate !schematicOnPageConnectorTemplate !schematicSymbolPortTemplate

Similar Keywords:

hotspotGrid hotspotNameCaseSensitive hotspotNameDef hotspotNameRef noHotspotGrid nominalHotspotGrid ripperHotspotRef

Constraints:

1. The following constraint applies to this context: All contexts
All hotspots must lie on the hotspotGrid, both directly and after instantiation.
(See also similar constraint in: hotspotGrid)

2. The following constraint applies to this context: All contexts
A hotspot can only lie on an interconnect when it is coincident with one of the points in the point list of the interconnect.

3. The following constraint applies to this context: All contexts
A hotspot may not be referenced by more than one schematicNet or schematicBus.
(See also similar constraint in: schematicNet)

Description:

A hotspot defines a point to which connections of nets or busses may be made in a schematic. It has no inherent width, so a schematicNet or schematicBus of any width may be connected to a hotspot. However, schematicWireAffinity may be used as a guideline to specify what type of interconnect (specified by schematicWireStyle) a particular hotspot is to be connected to.

A hotspot cannot lie on an interconnect unless the hotspot point is coincident with one of the points in the point list of that interconnect.

Example:

(hotspot (pt 20 30))

This example illustrates a hotspot defined at position (pt 20 30).

hotspotConnectDirection

hotspotConnectDirection ::= '(' 'hotspotConnectDirection'
	{ <fromBottom> | <fromLeft> | <fromRight> | <fromTop> } 
	')'

Used by:

<hotspot

Description:

HotspotConnectDirection defines the preferred direction of connections made to a hotspot.

The default value is (hotspotConnectDirection (fromBottom) (fromLeft) (fromRight) (fromTop)), meaning that connections may be made from any direction.

The preferred direction is defined in the coordinate space of the hotspot and would be transformed if the item containing the hotspot is transformed.

This attribute is for guidance of the CAD system only and it is not a semantic error if a connection is made to a hotspot from a direction that does not correspond with this attribute.

Each direction keyword represents a preference for a connection direction towards the center within the quadrant shown by the bold lines in the diagram below.

Example:

(hotspot ...
   (hotspotConnectDirection (fromTop)) ...)

In this example, the connection should be made to the top of the hotspot.

hotspotGrid

hotspotGrid ::= '(' 'hotspotGrid'
	lengthValue
	')'

Used by:

!schematicMetric

Similar Keywords:

hotspot noHotspotGrid nominalHotspotGrid

Constraints:

1. The following constraint applies to this context: All contexts
All hotspots must lie on the hotspotGrid, both directly and after instantiation.
(See also similar constraint in: hotspot)

Description:

HotspotGrid specifies a grid on which all hotspots must lie, either directly or after instantiation.

It is a semantic error if a hotspot lies off grid, and therefore the reader can rely on this grid being adhered to, and the writer must ensure that a correct value is used. If there is no hotspot grid, then noHotspotGrid is used instead.

Example:

(schematicUnits
   (schematicMetric
      (setDistance (unitRef mm_10))
      (hotspotGrid 10)))

In this example, all hotspots will lie at points with x and y coordinates exactly divisible by 10.

identifier

alpha | '&' | '_' 
{ alpha | digit | '_' }

Used by:

k1KeywordNameDef k1KeywordNameRef k2FormalNameDef k2FormalNameRef *k2Literal nameDef nameRef *userData userDataTag

Description:

Identifier is a basic token type; it is used for name definition, name reference and keywords. It contains alphanumeric or underscore characters and must be preceded with an ampersand if the first character is not a letter or underscore. This will normally be recognized by a lexical scanner.

Case is not significant in identifier. There are no reserved identifiers, except within k1KeywordNameDef. The length of an identifier must be between 1 and 255 characters, excluding the optional ampersand character. Identifiers are terminated by whiteSpace, quotation marks or by a left or right parenthesis.

Example:

a12
&a12
A12
abc
&12s
&120

The first three identifiers in this example are identical. The last two must include the ampersand.

	instanceNameDef

extendInstanceDef extendInstanceMemberDef instanceConfiguration instanceMemberRef instanceNameCaseSensitive instanceNameDisplay instanceNameRef instancePortAttributeDisplay instancePropertyDisplay instancePropertyOverride instanceRef instanceWidthDisplay pcbAllocatedInstancePort pcbComponentAllocatedInstance pcbEmbeddedDieTerminalToeprintInstanceRef pcbFootprintInstance pcbFootprintInstanceRef pcbFootprintToeprintInstanceRef pcbInstanceNets pcbNonSpecificSubLayoutInstance pcbPadstackInstance pcbPadstackInstanceBoardFixingPlace pcbPadstackInstanceBumpedBondPadAttachmentPlace pcbPadstackInstanceEmbeddedBareBondPadAttachmentPlace pcbPadstackInstanceIntendedUsage pcbPadstackInstanceJumperConnectionAttachmentPlace pcbPadstackInstanceMechanicalSecuringPlace pcbPadstackInstancePrintedComponentTerminalPlace pcbPadstackInstanceRef pcbPadstackInstanceRoutingViaPlace pcbPadstackInstanceSolderBallAttachmentPlace pcbPadstackInstanceSurfaceMountElectricalPinPlace pcbPadstackInstanceSurfaceMountSecuringPinPlace pcbPadstackInstanceTabAttachmentPlace pcbPadstackInstanceTestPointPlace pcbPadstackInstanceThroughHoleElectricalPinPlace pcbPadstackInstanceThroughHoleSecuringPinPlace pcbPadstackInstanceWirebondAttachmentPlace pcbSubLayoutInstanceNameCaseSensitive pcbSubLayoutInstanceNameDef pcbSubLayoutInstanceNameRef pcbSubLayoutInstancePhysicalNetRef pcbSubLayoutInstanceRef pcbTestCouponInstance external

Description:

Instance allows a cluster to be referenced within a view of another cell to create the instance hierarchy of a design.

An instance of a cluster means that some mechanism is required to select from that cluster the view which is most appropriate. The configuration of views applicable to a particular design can be specified using clusterConfiguration.

The representation of the instance in a page is achieved by using the construct schematicInstanceImplementation, which selects, in the case of a schematic page, a schematic symbol from the referenced cluster.

The instanceWidth attribute can be used to indicate that the instance is wide. In the context of a schematic view, the wide instance is represented by a single implementation.

If instanceWidth is greater than one, all attributes of the instance apply equally to each member of the set. This includes properties (property), instancePortAttributes, propertyOverrides, but excludes nameInformation, which applies to the wide instance as whole.

Example:

(instance nand12 
   (clusterRef C1 (cellRef nand)) ...)

The above example describes an instance named nand12 of the cluster named C1 of the cell named nand.

instanceConfiguration

instanceConfiguration ::= '(' 'instanceConfiguration'
	instanceNameRef
	clusterConfigurationRef
	')'

*clusterConfiguration

Constraints:

1. The following constraint applies to this context: All contexts
When a clusterConfiguration configures a view of a cell through a nested viewRef construct, all of the instances in the specified view should have an associated clusterConfiguration construct. This association can be direct through the use of an instanceConfiguration or indirect via the use of a defaultClusterConfiguration.
(See also similar constraint in: clusterConfiguration, defaultClusterConfiguration)

Description:

InstanceConfiguration selects a configuration for a particular instance in a view. This is done by referencing a clusterConfiguration within the cluster of the instance referenced by instanceNameRef. Therefore, the name referenced by clusterConfigurationRef must exist in the cluster instantiated by the instance named instanceNameRef.

It is not mandatory to specify an instanceConfiguration for each instance. During the specification of configuration, if an instance has no associated instanceConfiguration, the default cluster configuration of its instantiated cluster is assumed.

If the referenced instance has an instanceWidth greater than one, the configuration applies to all member instances equally.

Example:

(instanceConfiguration BLOCK1
   (clusterConfigurationRef CONFIG1))

instancePortAttributes

instancePortAttributes ::= '(' 'instancePortAttributes'
	extendPortDef
	{ <acLoad> | comment | <designator> | 
	<directionalPortAttributeOverride> | portDelay | portDelayOverride | 
	portLoadDelay | portLoadDelayOverride | portPropertyOverride | property | 
	<unused> } 
	')'

Used by:

*instance

Similar Keywords:

port

Constraints:

1. The following constraint applies to this context: All contexts
The directionalPortAttributeOverride must correspond to the portDirection of the port being overridden.
(See also similar constraint in: directionalPortAttributeOverride, portAnnotate)

Description:

InstancePortAttributes is used to attach or modify properties and attributes of the occurrence of a port within an instance. InstancePortAttributes refers to the port instance and not the port definition in the cell cluster.

The port instance inherits all inheritable properties and attributes of the port in the instantiated cluster. When the properties are inherited and not fixed, the values may be overridden within instancePortAttributes for this particular instance. Attribute values may also be overridden, e.g. acLoad given in instancePortAttributes overrides the value (if any) given on the port.

The directionalPortAttributeOverride must match the portDirection of the original port. Direction specific attributes may be overridden within this construct.

These properties and attributes may be displayed using instancePortAttributeDisplay.

Within the context of any one instance, each extendPortDef must be unique.

Example:

(cell LS04 ...
   (cluster C1 
      (interface (interfaceUnits ...)
         (designator "UXXX")
         (port in (inputPort)
            (designator "XX"))
         (port out (outputPort)
            (designator "QQ")))
      (clusterHeader ...)
      (schematicSymbol primary_symbol 
         ...)))
(cell Top_level_schematic ...
   (cluster C1
      (interface ...) ...
      (schematicView schematic_sheet
         (schematicViewHeader ...)
         (logicalConnectivity
            (instance &1
               (clusterRef C1 (cellRef LS04))
               (designator "U1")
               (instancePortAttributes in
                  (designator "1"))
               (instancePortAttributes out
                  (designator "2"))) ...)
         (schematicImplementation ...))))

In this example, a cluster C1 of cell LS04 will be created in every case with designator "UXXX" and with pin designators "XX" and "QQ", unless these lower-level designators are overridden by higher-level designators, such as those that appear in instance 1. In this instance, and only this instance, the designators are specified to be "U1" with pins "1" and "2".
