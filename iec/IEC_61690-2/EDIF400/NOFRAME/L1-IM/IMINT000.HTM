Part I: General introduction

1 Organisation of the information model

At present, the information model for EDIF Version 4 0 0 Level 1 consists of a total of 35 schemas. Figure 1.1 shows the structuring of schemas in the information model. Some schemas contain general information which is useful in the definition of other schemas. On the other hand, some schemas are viewtype specific. At present, the information model completely describes the connectivity, schematic and PCB/MCM viewtypes.

Figure 1.1: The structuring of schemas in the information model for EDIF Version 4 0 0 (Level 1)
Viewtype independent schemas

  • edif_information_model - provides the information held by an EDIF file.

  • library_model - contains the technology information of a library.

  • hierarchy_model - describes the hierarchical information of a cell.

  • design_hierarchy_model - holds annotation data relating to a design hierarchy.

  • instantiatable_object_model - defines various types of reusable template.

  • logical_connectivity_model - specifies view-wide connectivity.

  • design_management_model - provides design management information.

  • documentation_model - describes the documentation provided for an object.

  • geometry_model - describes geometrical concepts.

  • display_model - describes graphical primitives.

  • support_definition_model - provides general entity, type and function definitions which are used by other schemas.

  • unfinished_view_model - provides "stubs" for masklayout, symboliclayout, logicmodel and behavior viewtypes.

Connectivity view schemas

  • connectivity_view_model - describes the connectivity viewtype.

  • connectivity_structure_model - describes the structural connectivity of the connectivity view.

Schematic view schemas

  • schematic_view_model - describes the schematic viewtype.

  • schematic_implementation_model - describes the structural implementation of a schematic view.

PCB/MCM view schemas

  • pcb_mcm_view_model - describes the PCB/MCM viewtype.

  • pcb_assembled_board_model - describes the implementation of a PCB/MCM view.

  • pcb_package_model - describes a package which is a mechanical holder for a circuit.

  • pcb_mountable_package_model - describes the mounting information of a package.

  • pcb_part_model - describes parts (analogous to a component data book).

  • pcb_sub_layout_model - describes footprints, toeprints and other sublayouts on a bare board.

  • pcb_technology_model - describes the physical structure of a bare board and various technology rules which guides a designer (or CAD system) to create a layout which is manufacturable.

  • pcb_material_model - describes the materials which may be used during the construction of a bare board.

  • pcb_fabricate_model - describes the fabrication primitives.

  • pcb_board_subset_model - describes the primitives to be used in a drawing.

  • pcb_drawing_model - describes various types of drawing which are used as documentation of a PCB/MCM view.

  • pcb_mcm_instantiatable_object_model - describes various types of reusable template for PCB/MCM view.

  • mcm_die_physical_model - describes the interface of a die which is mounted onto an MCM.

  • mcm_mountable_die_physical_model - describes the mounting information of a die.

Level 1 specific schemas

  • expression_model - describes different types of expressions supported by Level 1 EDIF (see chapter 5).

  • frame_model - defines frames which allow users to repeatedly or conditionally include a subcircuit in a design (see chapter 4).

  • parameter_model - defines various types of parameters which are used to support parameterization of cells.

  • connectivity_frame_model - describes the structural connectivity of a frame in a connectivity view.

  • schematic_frame_model - describes the structural connectivity and the implementation information of a frame in a schematic view.

Part II: EDIF concepts (Level 1)

2 Introduction to Level 1

Level 1 EDIF incorporates additional concepts to Level 0. The principal difference is that Level 1 cells may be parameterized. This means that the result of each cell may be significantly changed on each instantiation by passing values to the parameters. In addition, expressions may be passed as parameter values, thus allowing parameters at one level to control the value of parameters at the next level.

Ports, signals and instances may have explicit width expressions (including parameters as appropriate) in Level 1. Port width and signal width are implicitly equal to 1 in Level 0. Thus for example, a simple port in Level 1 may represent any number of actual bits on expansion of a design. Port instances use a connected_signal_index_generator to resolve bitwise connectivity within the signal.

Another major feature introduced in Level 1 is that of frames. These are structures which permit the conditional inclusion or the repetition of circuit descriptions, based on the values of parameter expressions. For example, a cell may have a parameter which is used to control the number of stages in a shift register. This permits a very compact representation of a large class of actual circuits, provided that the receiving system is capable of interpreting such descriptions.

Another Level 1 feature which has been introduced is that of connectivity tags. These are associated with certain signals in order to represent latent connectivity at Level 1. They may be fully interpreted only after design expansion, where all expressions may be evaluated to literal values. At this time, any signals which have identical evaluated connectivity tags in the context of an expanded cell representation must be connected. This is necessary to describe connectivity in an environment where, for example, parts of a circuit may be repeated a number of times and that repetition count is not known until design expansion. The strategy of connectivity tags is significantly different from the explicit connectivity description used in Level 0. Level 1 incorporates both styles of explicit and latent connectivity.

Finally, the expansion names for objects such as instances may be described as expressions (including parameters as appropriate), so that distinct names may be generated for these objects during design expansion.

In the context of a design hierarchy, each instance of a Level 1 cell will be associated with a set of actual parameter values, and can thus be fully expanded. The expansion of a design which uses Level 1 cells may be performed as a CAD operation on the data transferred through EDIF. It is this operation that uses the semantics of Level 1 descriptions. It is important to note that a Level 1 cell description cannot be converted to a Level 0 cell, even in principle. For any given set of parameter assignments a fixed Level 0 cell can be generated which is equivalent to the original for these values only. However, a Level 1 cell corresponds to an unlimited number of Level 0 cells.

In the situation where a system cannot process parametric design information, a Level 1 file cannot be converted without loss. However, it is possible to recover sufficient information to obtain a representation of a particular design. A reader has the option of expanding a complete design, and thus resolving all parametric features on entry. This will cause a significant data explosion, and will not result in a transfer of any parametric libraries. Another option would be to generate numerous Level 0 variations of each Level 1 cell, corresponding to each set of parameter values which are applicable in a particular design hierarchy. This may be a practical option for a design which is predominantly Level 0, but uses a small number of Level 1 cells in a limited number of ways. In any case, the attempt to retrieve information from a Level 1 EDIF file into a system which does not support frames or parametric descriptions should be recognised as a non-trivial operation, and certainly not just a format translation exercise. At best, this can retrieve only partial information from the file -- for example, it would not permit any redesign or cell reuse at a parametric level.
